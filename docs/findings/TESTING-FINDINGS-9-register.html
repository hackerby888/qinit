Qinit Divergence Register

Six and a half thousand QPI contracts, ported from adversarial Solidity, compiled by the TypeScript backend and by clang, executed on a byte-identical call script, and compared by the K12 digest of their final state. Where the two disagree, one of them is what the chain does. Round 6 added a third opinion — core’s own WAMR runtime — but round 7 found it had been comparing one artifact with itself, so that table is withdrawn and replaced by a measured one. This is every disagreement the seven rounds turned up — and, at the end, a proposed fix for each one, none of them applied.

The fifteen compiler findings

F213

A constant name is global, and the last declaration wins

critical55 rows red

Every read below is fully qualified, so C++ has nothing to disambiguate and clang's column is simply correct. The TypeScript backend returns the value of the last constant declared under that name — across namespaces, across enum types, and across kinds of declaration: an enum constant overwrites a file-scope constexpr of the same name. Qualification is the fix a developer reaches for when two declarations collide; here it is accepted and ignored. 

namespace Alpha    { enum Level     { Low = 1,   High = 2   }; }
namespace Beta     { enum Level     { Low = 100, High = 200 }; }
namespace TwinName { enum FirstKind { Only = 7 }; }
namespace OtherName{ enum SecondKind{ Only = 9 }; }
static constexpr uint64 Shared = 5;
namespace WithEnum { enum Kinds     { Shared = 55 }; }

  read                                clang   TypeScript
  Alpha::Low                              1         100
  Alpha::High                             2         200
  Alpha::High * Beta::Low               200       20000
  TwinName::Only                          7           9
  Shared      (file-scope constexpr)      5          55
  WithEnum::Shared                       55          55
TypeScript backend

Compiles, runs, writes the wrong number into contract state. No diagnostic, no ambiguity report.

clang — what the chain does

Resolves each qualified name to its own declaration. A four-namespace ladder ORs to 15; TypeScript answers 8.

Confirmed on core’s own runtime Round 6 ran both artifacts under core’s WAMR host. Each reproduces its simulator answer exactly, so the wrong constants are in the wasm that would be deployed — not an artefact of how the simulator resolves names.
Why this is the worst one here F201, F205, F209, F211 and F214 refuse to compile, so the developer finds out. This one is silent and arithmetic. Round 4 recorded it as an enum-constant problem; round 5's value probes — same-named things whose values differ — showed the rule is broader. Three earlier rounds compared struct sizes and offsets, which a mis-resolution between identically shaped types cannot disturb.

F221

addMillisec advances the clock but never the calendar

high6 rows red

Adding a whole day’s worth of milliseconds moves the time of day correctly and leaves the date exactly where it was. The boundary is exact: everything below one full day agrees on both backends, and the divergence appears the moment the carry chain has to produce a day. Two days lose two days, so the carry is discarded rather than truncated — and the call returns true in every row.

Where it comes from addMillisec (qpi_date_time.h:515) forwards to the eight-argument add(), which carries micro → milli → sec → minute → hour, writes the time fields with setTime, and only then — if the resulting day carry is non-zero — folds it into days and tail-calls the three-argument add() to move the date. It is the clearest argument this campaign has produced for keeping both oracles rather than treating the hand-derived rows as the stronger one.

F217

A block-scope local shadowing an outer name is refused

mediumpinned

C99 block scoping: a name redeclared inside a block binds only from its declaration to the end of that block. clang accepts the contract and returns 1, 20, 300, 1 — confirmed byte-identically on core’s own WAMR host. The TypeScript backend refuses it with two diagnostics, and they are not equally interesting. 

static constexpr uint64 tier = 1;

locals.atOne = tier;            no local `tier` in scope yet -> the file constant
{
    uint64 tier = 20;
    locals.atTwo = tier;        the block's own binding
    {
        uint64 tier = 300;
        locals.atThree = tier;  the innermost binding
    }
}
locals.afterBlocks = tier;      control: the file constant again
TypeScript backend

error: 'tier' is used before its declaration

error: 'tier' shadows a declaration in an enclosing scope — locals share one slot per name, so shadowing is not supported

clang — what the chain does1, 20, 300, 1

Each block’s binding wins inside it, and the file constant is visible again once both blocks close.

The second diagnostic names the cause; the first is the finding “Locals share one slot per name” is a fair statement of a design limit — the backend’s locals model is flat, so a block cannot introduce its own binding. But locals.atOne = tier is read before any block declares a local tier, so in C++ it unambiguously names the file-scope constant. Calling that a use-before-declaration means the block-local declaration is being hoisted over the whole entry body — which is precisely what C99 block scoping exists to prevent, and what the Solidity test it was ported from (scoping/c99_scoping_activation.sol) was written to pin down.

F204

An out-of-range shift diverges only when the count folds

low–medium5 rows red

x << n with n >= width is undefined behaviour in C++, so neither backend is wrong. What is reportable is that clang answers the same expression two different ways depending on whether it folds — and that testing under --compiler typescript therefore cannot predict the on-chain answer. 

uint64 value = 1, count = 254
                     folded count   runtime count   self-consistent
TypeScript                  2^62            2^62   yes
clang                          0            2^62   no

2^62 is 1 << (254 mod 64) — what wasm's i64.shl does; it masks the count to six bits.
in-range controls agree everywhere: foldedInRange = runtimeInRange = 8 on both.

The width sweep bounds it: of 16 ShiftRhsWiderThanLhs variants, the ones that diverge are exactly the 32- and 64-bit widths with constSource=constexpr. Narrower widths agree because integer promotion widens them to int first. Without the constSource axis this would have looked like an ordinary width-dependent difference.

Confirmed on core’s own runtime Round 6 ran both artifacts under core’s WAMR host, which reproduces each backend’s row exactly. clang’s self-inconsistency is real on the production runtime, not a folding artefact of the test harness.

Seven defects in the harness and the engine recorded because an unrecorded generator bug looks like a compiler finding the next time someone reads the scoreboard

F219

The parity sweep compared one artifact with itself

buildContractWithClang and buildContractWithTypeScript both write <outDir>/<contractName>.wasm, and the sweep passed both the same directory. The TypeScript build ran second, overwrote clang’s artifact, and the run loop then read that one file twice — once labelled clang, once typescript. Round 6’s parity table therefore describes the TypeScript artifact twice, and real clang coverage under the third oracle was zero. Three confirmations: 357 of the 385 both-built contracts produced byte-identical rows, the 28 exceptions being the ones where the TypeScript build was refused and never wrote a file; and AccountBookWithIterationOrder’s clang artifact imports zero unregistered natives yet was scored shim-trap, a verdict that branch cannot reach. The part worth dwelling on is the validation. Round 6 offered “the shim-trap set is the same 76 contracts on each backend” as the check that made the run credible. But clang inlines KangarooTwelve into the module while the TypeScript backend imports it, so those sets should not have matched — their matching was the clearest possible evidence of the collision. A number was read as confirming the result when it was the disproof. fixed with per-backend output directories, plus a guard that aborts the sweep if two independently-produced artifacts are ever byte-identical — the condition that would have caught this on day one. Third defect in two rounds caught by a classification looking wrong, and the second caused by an artifact-path assumption; F218 was the first, one commit earlier.

F208

The simulator's committee is not reproducible between runs

qpi.computor(i) is generated per simulator instance, so a contract that stores qpi.computor(0) produces a different digest on every run — including two runs of the same backend, which is how it was caught. This is an engine defect, not a harness one. mitigated · the harness pins indices 0..675 before every run; it cannot pin more, because the override is keyed by raw index while the fallback wraps modulo committee size. Fixing it properly belongs in the engine.

F202

The nested-placement rewrite also rewrote the out-of-struct guard

placement=nested moves state members into an Inner struct and rewrites state.mut().X to state.mut().inner.X. Unconditionally — so it also rewrote placementGuard, the member that deliberately stays outside, which is the entire point of it. Thirteen contracts came back both-rejected, testing nothing. fixed with a negative lookahead · and it is this campaign's own evidence that two backends agreeing on a rejection tells you nothing about whether the contract was meant to be rejected

F206

The temporaries axis hoisted a function's locals into state

temporaries=stateScratch moves an entry's locals into a scratch sub-struct of StateData. Applied to a function, that makes a read-only entry write through state.mut(), which both build gates refuse — eleven contracts came back both-rejected. fixed · the axis now rewrites procedures only; the function variant renders identically and is dropped by the dedup

F207

entryOrder reordered entries whose types depend on each other

Where one entry's _locals names another entry's _input, declaring the contract's entries back to front emits the member before its type exists. Three ModifierAsPrivateFunction variants did exactly that. fixed · the axis stands down on such a dependency, and a corpus-wide control now walks every emitted contract asserting the invariant, so the next reordering axis cannot reintroduce it quietly

F218

The parity sweep manufactured 28 false divergences

It built its TypeScript side with the raw compileContractWithTypeScript driver, which skips the build gate. For a contract the gate refuses — F217’s block shadowing, the namespace alias — the raw driver returns an empty module rather than failing, and the sweep dutifully compared that empty module against WAMR and called the difference a divergence. Every one of the 28 read DEPLOY-FAILED(unexpected end of module) with zero imports. fixed by using buildContractWithTypeScript · and the difference is in acceptance, not codegen: for a contract the gate accepts, both paths emit byte-identical wasm. This is the exact trap F217’s notes describe, written one commit earlier, then walked into again in a different tool in the same round.

F216

A 3,600-tick script reads as a hang

hostcalls/TimePackedDateAndTime advanced the simulator through an hour — about forty seconds per backend, and with four workers competing it exceeded the shard deadline. Worth recording because of what it looked like: a hang in the scoreboard is otherwise the signature of a compiler that does not terminate, which is exactly F210. fixed · the script now advances 240 ticks and crosses the same minute and hour boundaries; the re-run is clean at 0 hang

Proposed fixes nothing here has been applied — this is a menu, not a changelog

Each card names where the defect actually lives, what the change would be, and what it would cost. The badge says how far the investigation got: verified means the root cause was read in the source and the mechanism reproduced against a probe; located means the responsible code was identified by reading but the mechanism was not separately confirmed; proposed means only the direction is known and the root cause is still open. Nothing below has been applied to the compiler.

One change would cover three of them

A non-addressable value gets a substitute invented for it, rather than being materialised or refused

F203 and F221 are the same mistake in two places. When emitAddress cannot give an address for an expression — a computed temporary, or a scalar living in a wasm local — the caller does not fail and does not materialise it properly. It substitutes something: K12 substitutes literal address 0 and hashes whatever the module has at the bottom of linear memory; argAddr substitutes a throwaway copy, which is right for a const T& and silently discards every write for a mutable one. F220 is the same shape a third time in spirit: an unhandled iterator method returns null and falls through to whatever handles an unrecognised call, rather than saying so.

So there is a policy fix available that is larger than any single card: make a null address a hard error at every site that currently invents a substitute, and give the two legitimate cases (hash a computed value, pass a mutable reference to a non-addressable lvalue) real materialisation with copy-back. That converts three silent wrong answers into either correct behaviour or a diagnostic, and it is the difference between a compiler that is wrong and one that is honest.

F213

Register unscoped enum members under their enclosing namespace, and stop the bare name being last-write-wins

verified
Root cause
semantics/declaration-index.ts:429. For namespace Alpha { enum Level { Low }; } the member loop registers Alpha::Level::Low, Level::Low and the bare Low — but not Alpha::Low, which is the spelling C++ requires for an unscoped enum member in a namespace. So the correctly-qualified read misses, falls through to scopedConstantKeys in constant-evaluator.ts:49, and is resolved from the bare tail in a single flat map where the last enum declared won. The same loop does constexprInit.delete(key) on the bare key, which is how an enum constant erases a file-scope constexpr of the same name.
Change
Two parts. (1) add scopePrefix to memberScopes for unscoped enums (not enum class), so Alpha::Low resolves to Alpha's own declaration — additive, and on its own it fixes every qualified read in the finding. (2) stop the bare key being claimed blindly: registerScoped and BareNamePolicy already exist (shared/enums.ts:436) but this loop bypasses them with a raw .set(). Add an AMBIGUOUS policy so a bare name claimed twice with different values is marked, and have resolveConst emit a diagnostic instead of returning whichever won.
Risk
Part 1 is low — it adds keys, it does not move existing ones. Part 2 will surface real ambiguities in contracts that compile today, as new errors; that is the point, but it wants a corpus run before it ships. It also overlaps F205, whose Helper case is a lookup-order question this policy touches.
F203

Materialise a computed K12 argument into scratch instead of hashing address 0

verified
Root cause
backend/wasm/calls/host-intrinsic-call.ts:114: emitAddress(context, callArguments[0]) ?? "(i32.const 0)". A computed argument — input.a + input.b, input.a * 1 — has no address, so the fallback fires and the call hashes sizeof(T) bytes of linear memory at offset 0. That is why the digest is not the K12 of any value in the contract.
Change
Route the input through argAddr (memory/memory-operations.ts:35), which already allocates a scratch slot and stores the value — the same thing every other by-value aggregate argument does. Then delete the ?? "(i32.const 0)": a K12 whose input cannot be addressed must fail, never hash the wrong bytes.
Risk
Low and strictly corrective. Any contract currently hashing address 0 changes its digest — which is the whole point, and none of them can have depended on the old value.
F221

A mutable reference bound to a non-addressable lvalue silently gets a copy

verified
Root cause
memory/memory-operations.ts:35, argAddr. When emitAddress returns null it allocates a scratch slot, stores the value, and hands the callee that address. Correct for const T&; for a mutable T& every write lands in the copy and nothing reads it back. A scalar by-value parameter lives in a wasm local, which has no address, so it always takes this path.

Confirmed by probe rather than inferred: add(0,0,5, 24,0,0,0,0) — five days plus a 24-hour carry, which the C++ folds together through addWithoutOverflow(days, dayCarry), writing through a reference to the by-value parameter days — gives day 7 under clang and day 6 under the TypeScript backend. References bound to locals propagate correctly; the whole carry chain above this step works.
Change
Three options, smallest first. (a) Fail closed: when a mutable reference argument is not addressable, emit a diagnostic. Turns a silent wrong answer into a refusal, a few lines, no behaviour to get wrong. (b) Copy back: after the call, load the scratch slot and store it to the source lvalue. Fixes the common case; needs the call site to hold a write path back to the source local. (c) Address-taken promotion: in functions/local-collector.ts, spill any scalar local or parameter whose address is taken anywhere in the function to a stack slot for its whole lifetime. The principled fix, and the one that makes references behave like C++ everywhere rather than at call sites the compiler happens to recognise.
Risk
(a) is safe but will reject QPI code that works on the chain today — including DateAndTime::add itself, so it cannot ship alone. (b) is contained. (c) touches every function's frame layout and wants the full corpus plus the WAMR parity sweep behind it.
F220

Pass the iterator's selector arguments instead of discarding them

verified
Root cause
backend/wasm/calls/containers.ts:523 calls materializeSelect(context, undefined), and undefined is the code path that builds any(). The same buffer is then passed for both the ownership and the possession parameter of $lh_assetEnumerate.
Change
Materialise each selector from its own argument — callArguments[1] for ownership, and callArguments[2] for possession on an AssetPossessionIterator (an AssetOwnershipIterator keeps undefined, which correctly means any()). materializeSelect already handles any, byOwner, byPossessor, byManagingContract, brace initialisers and a whole-struct copy, so no new machinery is needed. The two select structs are layout-identical in qpi_assets.h — id, uint16, two bool — so reusing the ownership layout stays correct.
Risk
Minimal: one extra 36-byte scratch slot per begin(). Worth fixing in the same pass: the seven accessors that fall through to null (issuer, assetName, issuanceIndex and friends) and the unrecognised AssetIssuanceIterator — at minimum make them a diagnostic rather than a silent fall-through.
F200

Do a 32-bit signed division at 32-bit width so wasm's defined trap can fire

verified
Root cause
backend/wasm/expressions/binary-expression.ts:159. The whole arithmetic model is i64 with a wrap applied afterwards for narrower types, so division emits i64.div_s regardless of operand width. At 64-bit width INT32_MIN / -1 is representable as 2147483648, so nothing traps and the wrap then produces -2147483648. clang divides at the declared width and gets i32.div_s, which wasm defines to trap here.
Change
In the DIVIDE case, when the operands are signed and 32-bit, wrap both to i32, emit i32.div_s, and sign-extend the result back into the i64 value model. The surrounding code already has the width and signedness to hand (cv.width, unsigned) and already special-cases width 4 for the other operators.
Risk
A contract that today survives this division starts trapping — which is what the chain does, so it is a correction rather than a regression. MODULO on the line below has the identical problem and should move with it.
F204

Diagnose a constant shift count wider than its operand rather than choosing a semantics

located
Root cause
binary-expression.ts:139: shiftCount masks to 31 for 32-bit operands and otherwise leaves the count to i64.shl's implicit mask of 63. clang's constant folder and its runtime path disagree with each other, so there is no correct answer to match — the construct is undefined behaviour in C++.
Change
Do not pick a semantics. When the shift count is a compile-time constant greater than or equal to the operand width, emit a diagnostic and refuse. That is the only outcome that is right regardless of which backend the developer later builds with, and it is where the two provably differ.
Risk
Rejects code that compiles today. Bounded to a constant count, so it cannot fire on a runtime value, and any contract it rejects was already unpredictable across backends.
F212

Refuse a CALL from a function to a procedure, as the context types already do in C++

located
Root cause
clang refuses this through the type system — no viable conversion from 'const QpiContextFunctionCall' to 'const QpiContextProcedureCall' — because a function body is handed the read-only context. The TypeScript backend does not model that distinction at the call site, so the call is emitted and the state write goes through.
Change
Enforce it in the analyzer: an entry compiled as a function may not CALL a target registered as a procedure, and may not reach state.mut() transitively through one. The entry kind is already known where entries are registered, so this is a check rather than new machinery.
Risk
Low, and it closes a hole in the read-only guarantee that a caller may be relying on today without realising the chain would reject the same contract.
F217

Give each block its own binding instead of one local slot per name

proposed
Root cause
Stated by the backend's own second diagnostic: locals share one slot per name, so shadowing is not supported. The first diagnostic — calling a read of the outer name before any block a use-before-declaration — is the reportable half, and implies the block-local declaration is hoisted over the whole entry body.
Change
Key locals by (name, blockDepth) rather than by name in the local collector, so an inner block gets its own slot. If that is too large, the smaller fix is to stop the hoist: a block-local declaration must not affect name resolution before the block opens, which removes the false use-before-declaration while leaving shadowing refused.
Risk
The full change touches local allocation for every entry. The smaller one is contained to the resolver and only converts a wrong diagnostic into a correct one.
F214

Parse a full template argument list inside sizeof

proposed
Root cause
error: Expected r_paren but got comma (,) in sizeof expr — the sizeof operand is parsed as an expression that stops at the first comma, so any multi-argument template ends the parse. Every QPI container takes at least two arguments.
Change
Parse a type-id in sizeof(...), reusing the template-argument parser that already handles Array<uint64, 8> everywhere else — aliasing the type first already works, which shows the type parser is fine and only the sizeof operand path is narrow.
Risk
Contained to the parser, but sizeof(expr) and sizeof(type) have to stay distinguishable, which is the classic ambiguity here and wants tests on both spellings.
F215

Allow a member read on a substituted constant by materialising it first

proposed
Root cause
error: unsupported member read [id(4).u64._0]. The diagnostic naming id(4) rather than SELF says the constant is substituted before the member read is considered, leaving a member access on a value with no address — the same family as F203 and F221 above.
Change
Materialise the substituted constant into a scratch slot and read the member from it, which is what the one-assignment workaround does by hand today.
Risk
Low. Likely resolved for free if the systemic address policy above is adopted.
F209

Accept a leading :: and resolve it at global scope

proposed
Root cause
The qualified-name parser does not accept an empty left-hand side, so ::name is a parse error while Port::name in the same file is not.
Change
Accept a leading :: in the qualified-name production and resolve the tail against the global scope only, skipping the using-directive fallbacks — which is exactly what the qualifier means, and would also give F213 a spelling that is guaranteed unambiguous.
Risk
Low; additive syntax.
F205

Search class scope before file scope inside a member body

proposed
Root cause
C++ looks in class scope first inside a member function, so a PRIVATE_FUNCTION(Helper) hides a file-scope enum constant of the same name and the assignment becomes ill-formed. The TypeScript backend resolves to the constant and stores 3.
Change
Consult contract members before file-scope constants when resolving a bare identifier inside an entry body, and let the ill-formed assignment be a diagnostic. Best sequenced after F213, since both change constant lookup and F213's part 2 is the one that makes collisions visible at all.
Risk
Changes name resolution for every entry body — the highest-blast-radius item on this list relative to the size of the finding.
F211

Bound struct resolution and report the collision

proposed
Root cause
Not located. A nested struct whose name matches a file-scope struct recurses until Maximum call stack size exceeded. The obvious guess — that alias resolution lacks a depth bound — was checked and is wrong: resolveAliasType (expressions/conversions.ts:16) and declaration-index.ts:677 both bound themselves at 8. The unbounded path is somewhere else in struct-by-name resolution.
Change
Find the recursion first, with a stack trace from the crash. Then bound it and turn the collision into a diagnostic — a name collision deserves a message, not a crash, whatever the resolution rule turns out to be.
Risk
Unknown until the recursion is located.
F210

Find the unbounded loop behind the same-name alias hang

proposed
Root cause
Not located, and the natural theory is disproved. using Payload = Inner::Payload does not hang resolveAliasType, which stops after 8 hops. Something on a different resolution path does not terminate, and because the build gate runs for both backends it takes the clang pipeline down too.
Change
Reproduce under a profiler or with a hard iteration cap that reports where it was spinning — the repro is two lines and deterministic, so this is cheap to locate and only untouched because the contract is deliberately kept out of the corpus.
Risk
None to investigate. Highest priority of the unlocated three: it is the only finding that hangs the toolchain rather than producing a wrong answer or a refusal.
F201

Resolve alias chains to a fixed point in base-class lookup

proposed
Root cause
Not located. One and two alias hops to a base class are accepted and three is refused with unsupported member read. The depth bound in resolveAliasType is 8, so a simple hop limit is not the explanation; some other step in base-class member lookup resolves the chain only partially.
Change
Trace the member read for the three-deep spelling against the two-deep one and find where they diverge; the pair differ by one using declaration, so the bisect is already written.
Risk
Unknown until located; the corpus rows are 4 and it is a refusal, not a wrong answer.

Round 4 spent the same contract budget on half again as many distinct shapes — the variant cap dropped from 32 to 12 — on the argument that the archetype count, not the contract count, is the effective sample size. The red rows grow with the corpus because each finding's variants multiply, not because new defects appear: every red row in every round is one of the numbered findings and nothing else. Round 7 is the exception that proves it — its six extra red rows are F221, a genuinely new defect, in a family the corpus had never called before.

What the green rows are worth

The simulator, measured on both backends at last

Round 6’s version of this paragraph is withdrawn: F219 showed it had run the TypeScript artifact twice, so its clang column was never measured. Repaired and re-run, with the test shim widened from 5 natives to 20: across 105 contracts and 210 artifact runs, 195 agree, 0 disagree, 0 unreachable, and 15 refused by the TypeScript build gate. clang 105 agree — every contract built and ran — is the first real measurement of that backend against core’s runtime. The shim gap closed completely: 152 of 770 runs were unreachable before, 0 of 210 now. The sample is smaller than round 6’s 385, because the sweep was competing for four cores with the full differential run.

The oracle problem

Both backends share one build gate, one qpi.h, and one QubicSimulator. “6,514 matched” means they agreed with each other, not that they were right. F200, F213 and F204 run on core’s real WAMR host and reproduce their answers there, and round 7’s widened shim brings the hash-keyed and tick-reading contracts into range too. The rest still rest on the two backends disagreeing, and several cannot be settled this way — a compile refusal produces no artifact to run, and F220 lives in the asset region the shim deliberately does not cover.

The positive control

A suite that has never gone red is not evidence. Planting uint16: 2 → 4 in scalar-sizes.ts turned 126 of the 708 layout contracts red; restoring it returned all 708 to green. That also proves the compile cache's backend stamp, which would otherwise replay pre-mutation wasm and report a clean bill of health.

Stimulus coverage

So the green rows are not vacuous: the great majority of the 6,618 contracts move their state digest mid-script, and 357 make a cross-contract call. The ~179 hand-derived expect rows — 69 of them added this round, for DateAndTime and for HashMap removal — are the only assertions of correctness, and every one holds. They keep catching the author rather than the compiler: three of his errors in round 6, eleven in round 5, two more in round 7.

Not 6,091 trials

6,618 contracts from 449 archetypes is 14.7 variants each. Read the contract number as breadth of spellings. The variants earn their place as the axis bisector: when a mismatch appears, the sibling variants that differ in exactly one axis name the trigger — which is how F200 was pinned to sint32 and F204 to constSource=constexpr.

Only 2,780 are faithful ports

QPI has no revert, no uint256, no unbounded mapping and no reentrancy, so a Solidity test whose point was atomicity or 256-bit wraparound becomes a different test after porting. The corpus is a source of adversarial shapes, not evidence about Solidity semantics.

Where the remaining risk is

None of round 7’s three findings came from reading a big sweep’s red column. F219 came from a classification that looked wrong, F220 from reading the function that lowers a feature nobody had called, F221 from an archetype shipped without an expect row. The corpus’s real contribution was reproducing them across variants and showing F220 was not a fluke of one contract — worth having, but the finding rate per hour favoured reading the code over generating more of it. And the share-management API, where two earlier campaigns both found bugs, is still at zero call sites.
